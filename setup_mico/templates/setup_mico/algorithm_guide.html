    연마 시간은 어떻게 정해지는가

    CMP는 웨이퍼를 회전하는 패드에 눌러 깎아내는 공정입니다. 매번 같은 시간만큼 깎으면 두께가 흐릅니다 — 입고 두께가 다르고, 패드가 닳고, 장비가 쉬었다 돌기 때문입니다. MICO는 이 세 가지를 각각 학습해서 다음 웨이퍼의 연마 시간(또는 존 압력)을 정합니다. 이 문서는 그 세 학습값이 무엇을 보고 무엇을 계산하는지 그림으로 설명합니다.

    Pol_Time  =  Δ / RR_DB  +  OFFSET

    Δ = 깎아내야 할 두께 (입고 − 목표) · RR_DB = 지금 이 패드의 제거율 (Å/sec) · OFFSET = Idle 보정 (sec)
    → 이 식의 세 항이 각각 Pre_Thk_VM, Removal Rate, OFFSET 학습값입니다.

    왜 보정하나 전체 흐름 TIME vs PRESSURE ① Pre_Thk_VM ② Removal Rate ③ OFFSET ④ Simulation 학습값이 안 나올 때 용어
    문제

    고정 시간으로 깎으면 왜 두께가 흐르는가

    세 가지 변동 요인 — 그리고 각각에 대응하는 세 학습값

    연마량은 대략 제거율 × 시간 입니다. 그런데 제거율은 상수가 아니고, 출발점인 입고 두께도 상수가 아닙니다. 아래 그림은 아무 보정 없이 고정 시간으로 깎았을 때 후처리 두께가 어떻게 흘러가는지를 보여줍니다.

    문제 ①

    입고 두께를 모른다

    CMP 직전 두께를 매 웨이퍼 측정하지 않습니다. 사전공정 장비가 다르면 입고 두께도 다른데, 그 차이를 모른 채 같은 시간을 깎습니다.

    Pre_Thk_VM
    문제 ②

    제거율이 계속 변한다

    패드·디스크·헤드가 닳으면서 같은 조건에서도 깎이는 양이 달라집니다. 패드 교체 직후와 수명 말기의 제거율이 다릅니다.

    Removal Rate
    문제 ③

    쉬었다 온 장비는 다르다

    Idle 후 첫 장, 레이어가 바뀐 첫 장, 패드 교체(LC) 직후 — 정상 상태 모델이 맞지 않는 구간이 규칙적으로 발생합니다.

    OFFSET
    흐름

    데이터가 학습값이 되어 돌아오는 경로

    Merge → Module(학습) → MongoDB → Simulation → APC

    MICO는 학습과 적용이 분리되어 있습니다. 학습은 매시간 배치로 돌면서 MongoDB에 계수만 저장하고, 실제 웨이퍼가 들어올 때는 저장된 계수를 읽어 쓰기만 합니다. 그래서 학습이 오래 걸려도 생산이 기다리지 않습니다.

    읽는 법

    Set-up 화면(Category / SubCategory / Detail)에서 넣는 값은 전부 이 그림의 왼쪽 아래 웹 Set-up으로 들어가서, 어떤 파라미터를 어떤 역할로 쓸지를 정합니다. 즉 Set-up이 곧 알고리즘의 배선도입니다 — 코드를 고치지 않고 공정별 동작을 바꾸는 지점입니다.

    모드

    TIME과 PRESSURE는 무엇이 다른가

    같은 학습 파이프라인, 다른 제어 대상 — 평균 두께냐, 웨이퍼 안의 프로파일이냐

    Set-up의 FB_Type이 TIME 이냐 PRESSURE 냐에 따라 알고리즘이 제어하는 대상이 갈립니다. 두 모드는 학습 로직이 같고 y축(무엇을 0 기준으로 볼 것인가)만 다릅니다. 이 한 가지가 코드 전체에서 use_pressure / is_bias_type 분기로 나타납니다.

    항목TIME (13P)PRESSURE (존별 · ED/EX)
    맞추는 대상 웨이퍼 평균 두께 → Target 존 두께 − 13P 두께 → 목표 편차
    제어 변수 Pol_Time (연마 시간, sec) Pressure_1..n (존별 압력)
    0 기준값 Thk_Para − mean(Thk_Para) (Thk − Thk_13P) − (Target − Target_13P)
    RR 계산 시 post Thk_Para 실측값 Target + BIAS (편차를 되돌린 값)
    MA 최소 건수 10건 5건 (Thk_Para에 ED/EX 포함 시)
    RR 알람 발송 (3σ 이탈 시 Cube) 미발송 — TIME 파라미터 한정
    왜 PRESSURE는 13P를 빼는가

    존별 압력은 웨이퍼 안의 상대적 기울기만 바꿉니다. 평균 두께 자체는 TIME이 이미 맞추고 있으므로, PRESSURE 학습에서 절대 두께를 y로 쓰면 TIME 제어가 만든 변동까지 같이 학습해 두 루프가 서로 싸웁니다. 13P를 빼서 평균 성분을 제거해야 두 제어가 독립적으로 동작합니다.

    ① VM

    Pre_Thk_VM — 재지 않은 입고 두께를 추정한다

    사전공정 장비가 남긴 지문을 후처리 두께에서 역으로 읽어낸다

    CMP 직전 두께를 매 웨이퍼 측정할 수 없습니다. 그런데 같은 사전공정 장비·채널에서 나온 웨이퍼들은 비슷하게 두껍거나 얇습니다. Pre_Thk_VM은 이 규칙성을 이용합니다 — 과거 웨이퍼들의 후처리 두께에서 "패드 마모 때문에 생긴 추세"를 지우고 남은 잔차를 사전공정 장비별로 평균 내면, 그것이 곧 그 장비의 입고 두께 편차입니다.

    먼저: 두 갈래 경로 중 어디로 가는가

    Set-up에 Pre_Thk_Para_ITM(사전공정 실측 파라미터)이 있으면 그 실측값을 그대로 쓰고, 없으면 후처리 두께에서 역산합니다. 세 번째로, 실측값이 있어도 Pre_Thk_VM_Source = POST로 두면 강제로 역산 경로를 탑니다.

    Detrend — 후처리 두께에서 패드 추세를 지우는 3단계

    역산 경로의 핵심입니다. 후처리 두께에는 입고 산포와 패드 마모가 섞여 있습니다. 우리가 원하는 건 입고 산포뿐이므로, 패드 마모 성분을 먼저 지워야 합니다.

    왜 패드 사이클마다 잘라서 계산하는가

    장비별로 모으고, 전공정 파라미터로 한 번 더 보정한다

    잔차를 사전공정 장비·채널(pre_eq_ch)별로 설정 기간 (Pre_Thk_Period, 예: 7D) 만큼 이동평균하면, "이 장비에서 온 웨이퍼는 평균보다 이만큼 두껍다"는 값이 나옵니다. 이것이 저장되는 VM 학습값입니다.

    여기에 더해, 사전공정의 특정 계측 파라미터(Pre_Oper2~4)가 설정되어 있으면 그 값과 잔차 사이의 단순선형회귀를 하나 더 돌려 기울기·절편 (b1, b0)을 저장합니다. 적용 시점에는 두 가지가 더해집니다.

    VM  =  MA(잔차)장비별  +  Σn=2..4 wn · ( xn · b1n + b0n )

    그리고 Pre_Thk = Pre_Target + VM — Set-up의 고정 입고 목표에 학습된 편차를 얹은 값이 실제 계산에 쓰입니다.
    Pre_Oper(이동평균)를 끄고 회귀항만 쓰거나, 항목별 가중치를 바꾸는 것은 공정별 Simulation_Hub.py의 PRE_THK_FORMULA에서 조정합니다.

    ② RR

    Removal Rate — 지금 이 패드가 얼마나 깎는지

    소모품 사용량 대 제거율의 직선, 그리고 그 직선을 네 가지로 그리는 이유

    제거율은 정의부터 단순합니다. 깎인 두께를 걸린 시간으로 나눈 값입니다. Pre_Thk에는 방금 학습한 VM이 들어갑니다 — ①이 있어야 ②를 계산할 수 있는 이유입니다.

    RR  =  ( Pre_Thk − Post_Thk )  /  Pol_Time    [Å/sec]

    TIME Post_Thk = 실측 두께  ·  PRESSURE Post_Thk = Target + BIAS (13P 대비 편차를 되돌린 값)
    REV 파라미터(두께가 늘어나는 방향)는 부호를 뒤집어 (Post − Pre)로 계산합니다.

    패드가 닳으면 제거율이 떨어진다 — 그 기울기를 학습한다

    같은 데이터로 직선을 네 개 그린다

    전체 데이터로 그린 직선 하나만 쓰면, 어제 패드를 갈았는데도 지난 6개월 평균을 따라갑니다. 반대로 최근 것만 쓰면 데이터가 적어 흔들립니다. MICO는 성격이 다른 직선 네 개를 모두 학습해두고, 적용 시점에 가장 좁고 최신인 것부터 골라 씁니다.

    적용할 때의 선택 순서

    1. IF 모델 — 지금 소모품 사용량이 Pad_Seperation 이하면 초기 구간 전용 직선을 쓴다. 조건 : Pad_Seperation 설정됨 · 해당 구간 100건 이상 · 4등분 각 25건 이상
    2. current 모델 — 지금 붙어 있는 패드에서 뽑은 직선. 가장 최신 상태를 반영한다. 조건 : cycle 1 데이터 > RR_Count · 최신 타점이 12시간 이내 · 최근 PM 이후 웨이퍼 2장 이상
    3. weighted 모델 — 최근 날짜에 가중치를 준 직선. 조건 : 가장 최근 날짜 구간에 소모품 4구간이 모두 있고 각 25건 초과
    4. 전체 회귀 — 위가 전부 없을 때의 기본값. 항상 존재한다. 조건 : 없음 (4분면 조건을 통과해 학습이 돌았다면 항상 있음)
    current 모델의 안전장치

    current는 데이터가 적어 기울기가 튈 수 있습니다. 그래서 RR_Period가 설정되지 않은 경우 b1은 기준 모델(weighted 또는 전체)의 2배를 넘지 못하고 부호도 뒤집히지 못하며, b0는 기준값의 ±10% 안으로 묶입니다. 최신성을 취하되 폭주는 막는 구조입니다.

    직접 움직여 보기 — 패드 마모가 연마 시간에 미치는 영향 TIME 모드
    고정 Set-up 값
    Pre_Target 5500 Å · Target 4000 Å
    b1 = −0.0060 · b0 = 22.00 Å/s
    Pre_Thk = Pre_Target + VM5500.0 Å
    Δ = Pre_Thk − Target1500.0 Å
    RR_DB = 패드 × b1 + b022.000 Å/s
    Δ / RR_DB68.18 s
    Pol_Time = Δ / RR_DB + OFFSET68.18 s
    RR 알람

    TIME 파라미터에 한해, 최근 3건의 RR 평균이 전체 데이터의 ±3σ를 벗어나면 Cube로 알람이 갑니다. 제거율이 갑자기 올라가거나 내려간다는 뜻이고, 보통 소모품 이상이나 슬러리 문제의 첫 신호입니다. 학습값을 고치는 게 아니라 사람에게 알리는 장치입니다.

    ③ OFF

    OFFSET — 모델이 틀리는 구간을 따로 외운다

    Idle 이후·레이어 전환·패드 교체 직후에 필요했던 추가 시간

    Removal Rate 모델은 정상 연속 생산 상태를 가정합니다. 장비가 쉬었다 돌면 패드 표면 상태가 달라져 첫 몇 장의 제거율이 모델과 다릅니다. OFFSET은 이 차이를 "시간을 몇 초 더 줬어야 했나"로 환산해 IDLE 구간별로 저장합니다.

    IDLE 라벨 — 어떤 상황이었는지가 그룹 키다

    IDLE 라벨의미처리
    (빈 값) 정상 연속 생산 RR 학습에 쓰이는 유일한 구간. OFFSET 계산 대상이 아님 (저장 시 Normal로 표기)
    Idle_* 장비가 쉰 뒤 첫 웨이퍼 — 쉰 시간대별로 라벨이 나뉨 장비 × 레시피 × 라벨로 묶어 평균. 그룹당 5건 이상일 때만 저장
    Layer_* 직전 웨이퍼와 레이어(막질)가 달랐던 경우 Idle_*와 동일하게 처리
    LC_* 패드 교체(Life Cycle) 직후 구간 별도 함수에서 집계. Offset_Group='Y'면 장비 번호를 떼고 레시피 그룹 단위로 평균
    LC_T_* / LC_TB_* 패드 교체 + Truing(표면 다듬기) 수행 OFFSET을 강제로 0. Truing으로 표면이 새로 잡혀 정상 모델이 맞기 때문
    Offset_Group 옵션

    장비 대수가 많고 각 장비의 LC 데이터가 5건을 못 채우면 학습이 아예 안 나옵니다. Offset_Group='Y'는 IDLE 라벨에서 장비 번호를 떼어내 같은 상황끼리 합쳐 평균을 냅니다 — 개별 장비 특성은 포기하고 표본 수를 확보하는 쪽을 택하는 설정입니다.

    ④ SIM

    Simulation — 세 학습값을 다시 하나로 합친다

    시점 기준 결합(merge_asof)과 최종 제어값 계산

    학습이 끝나면 세 값은 서로 다른 MongoDB 컬렉션에 서로 다른 키와 시점으로 들어가 있습니다. Simulation은 이것을 웨이퍼 한 장 기준으로 다시 붙입니다. 이때 중요한 것이 그 웨이퍼가 흐르던 시점에 유효했던 학습값을 붙이는 것입니다 — 오늘 학습된 계수를 지난주 웨이퍼에 붙이면 검증이 무의미해집니다.

    결합 순서와 최종 계산

    Simulation_Get.simulate()는 TIME·PRESSURE 공통으로 아래 순서를 탑니다. 마지막 _finalize에서 모드에 따라 출력 컬럼이 갈립니다 — TIME은 Pol_Time, PRESSURE는 Pressure_1..n.

    #단계하는 일
    1_build_base_framemerge_df에서 해당 Oper/Recipe/APC 파라미터 행만 추출
    2_attach_pre_vm① VM 학습값을 사전공정 채널·시각 기준으로 결합
    3_attach_rr② RR 계수 4종(b1/b0 · weighted · current · IF)을 장비·레시피·시점 기준으로 결합
    4_attach_offset③ OFFSET을 장비·레시피·IDLE 라벨까지 맞춰 결합
    5_fill_learning_values남은 결측을 평균으로 보정, '-' 표기를 NaN으로 정규화
    6_apply_pre_thk_formula공정별 PRE_THK_FORMULA대로 Pre_Thk 조합 (이동평균 사용 여부·회귀항·가중치)
    7_finalizeRR 모델 우선순위로 RR_DB 결정 → 모드별 출력 컬럼 산출
    종합 — 세 학습값이 함께 움직일 때 TIME
    점검

    학습값이 안 나올 때 볼 것

    대부분은 알고리즘 오류가 아니라 표본 수 게이트에 걸린 것입니다

    증상가장 흔한 원인확인할 곳
    RR 계수가 아예 없다 소모품 사용량 4분면 중 한 구간이 25건을 못 채움 — 패드 수명 한쪽에만 데이터가 몰림 Set-up의 RR_Para(HEAD/PAD/DISK 중 무엇을 볼지)와 RR_Para_Max
    b1_current만 비어 있다 최신 타점이 12시간을 넘었거나, PM 이후 웨이퍼가 2장 미만이거나, cycle 1 데이터가 RR_Count 이하 장비 가동 이력 · RR_Count 설정값
    if_b1이 비어 있다 Pad_Seperation 미설정, 또는 그 구간 데이터가 100건 미만 / 4등분 각 25건 미만 Detail의 Pad_Seperation
